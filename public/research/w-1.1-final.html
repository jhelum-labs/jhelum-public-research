1. Executive summary

Outcome WAI-125M completed next-token pretraining successfully. It contains 123,688,704 trainable parameters, uses a 32,000-token BPE vocabulary and 2,048-token context, and completed 5,389 optimizer steps over approximately one full pass of the 2.825B-token training split.

The model is a decoder-only Transformer implemented from scratch with RMSNorm, rotary positional embeddings, causal scaled dot-product attention, SwiGLU feed-forward blocks, and tied input/output embeddings. The final run used an NVIDIA H100 and stabilized near 375,000–377,000 tokens per second after startup.

The strongest recorded checkpoint occurred at step 2,750 with validation loss 3.3804, corresponding to perplexity 29.38. Later validation measurements rose, so best.safetensors—not the final-step weights—is the recommended inference and fine-tuning starting point. The behavior is consistent with a functioning base language model: it generates readable, topical paragraphs but can hallucinate institutions, studies, quotations, and citations.

Research conclusion

The pretraining phase is technically successful, but the model is not yet production-ready. It remains a base continuation model rather than an instruction-following assistant. Production requires standardized benchmarks, test-set evaluation, Hugging Face-compatible packaging, supervised instruction tuning, safety evaluation, quantization, API serving, and monitoring.

Key experimental decisions

  • Use a raw-first pipeline with deduplication, then tokenize into uint16 binary files.
  • Reserve exact validation and test targets instead of relying on approximate file percentages.
  • Use a modern decoder-only design rather than copying GPT-2 exactly.
  • Train the full final model on H100 while keeping local 4 GB GPU inference as a deployment constraint.
  • Preserve both best and final checkpoints, plus a resumable latest.pt training checkpoint.

3. Final system design

WAI-125M is a causal decoder-only Transformer. Given a sequence of token IDs, it predicts the probability distribution of the next token at every position. Training minimizes token-level cross-entropy against the sequence shifted by one token.

Parameter accounting

The implemented architecture was checked before training. The recorded count was exactly 123,688,704 parameters, within the intended 123–125M range. Tied embeddings avoid maintaining a separate 32,000 × 768 output matrix.

Design lineage The causal Transformer follows the attention-based architecture introduced by Vaswani et al. The GPT-style objective follows decoder-only autoregressive language modeling, while RMSNorm, RoPE and SwiGLU are modernized implementation choices.

Preprocessing interruption and recovery

Cell 9 stopped after creating valid binary files. Instead of restarting the entire 17 GB preprocessing job, the existing train.bin, val.bin and test.bin files were inspected and finalized. The recovered counts were written to meta.json and manifest.json. This preserved 2.825B training tokens and avoided an expensive rebuild.

Integrity result Validation reached exactly 25,000,000 tokens and test reached exactly 5,000,000 tokens. The training split contained all completed remaining tokens: 2,825,248,272.

Data-quality limitation

Qualitative generations resemble web articles and occasionally invent studies, authors, journals and funding sources. This indicates that the corpus taught useful grammar and topical associations but retained noisy web-style patterns. Future corpus versions should strengthen source filtering, document quality scoring, language identification, near-duplicate removal, citation-pattern filtering, and personally identifiable information checks.

5. H100 training run

The final job used a detached Modal function with one NVIDIA H100. Dataset files were staged from Google Drive to a persistent Modal Volume, copied to local SSD, verified, and then consumed by the training loop. The notebook itself could remain on CPU because the detached training function owned the H100 container.

The difference between nominal scheduled tokens and available train tokens is 139,760 tokens—less than one optimizer step. The loader’s modulo behavior means the final step can wrap to the beginning of the binary dataset, effectively completing about one epoch.

Compilation failures and repair

  1. The first H100 attempt failed because CUDA Graph outputs were overwritten across repeated compiled invocations during gradient accumulation.
  2. A subsequent torch.compile change supplied both mode and options, which PyTorch rejects.
  3. The compile configuration was repaired by disabling CUDA Graphs through a single valid compile configuration.
  4. The resumed job started correctly, reached step 1, then sustained full H100 throughput and completed training.

What the curve suggests

  • The model learned rapidly: loss fell from 10.5419 at step 1 to below 4 by roughly step 900.
  • The best generalization point appeared around the midpoint of the one-epoch run at step 2,750.
  • A noisy instability band appeared around steps 2,790–2,880, where loss and gradient norms rose sharply.
  • Later train losses sometimes improved while validation remained worse than the best checkpoint, so final-step weights should not automatically replace best weights.
  • The validation series is sparse. More frequent, fixed-batch evaluation would separate genuine drift from validation sampling noise.

Checkpoint decision Use best.safetensors for inference, benchmarking and instruction tuning. Keep wai-125m-final.safetensors for research comparison and latest.pt only for resuming the optimizer state.

7. Generation-quality research

The final model generated coherent paragraphs from open-ended prompts. It maintained local topic consistency, used headings and bullet formatting, and produced mostly grammatical English. These are strong signs that next-token pretraining succeeded.

Reproducibility controls now present

  • Tokenizer and tokenizer metadata stored separately from weights.
  • meta.json and manifest.json record finalized binary split information.

  • A local VS Code CUDA notebook reconstructs the exact architecture and verifies the parameter count before loading weights.

Recommended production architecture

  • Immutable model registry: base, instruct, quantized and deployment versions with checksums.
  • Inference service: a single model worker with bounded context, token limits and request batching.
  • API layer: authentication, quotas, timeouts, schema validation and audit logging.
  • Safety layer: input classification, output moderation, blocked-token/pattern controls and escalation.
  • Observability: latency percentiles, GPU memory, generation length, error rate, safety flags and version tags.
  • Rollback: one-click return to the previous known-good model package.

11.3 Local 4 GB GPU target

The current FP32 checkpoint is approximately 472 MB and FP16 parameters are approximately 236 MiB, so the 123.7M model comfortably fits in 4 GB VRAM for inference. The main inefficiency is generation without a key/value cache: each new token recomputes the entire prefix. A production inference rewrite should add KV caching before latency optimization or deployment claims.

12. Conclusions

W-1.1 progressed from small experimental models to a complete 123.69M-parameter open-domain base language model. The final system successfully learned next-token prediction over 2.825B training tokens, sustained high H100 throughput, produced coherent English continuations, and saved a complete set of best, final and resumable artifacts.

The strongest evidence of success is not a single attractive sample. It is the combination of a decreasing training loss, a measurable best validation checkpoint, stable high-throughput execution, exact artifact preservation, and repeatable local loading. The strongest evidence of remaining work is equally clear: hallucinated citations, topic drift, unsafe continuations, sparse evaluation and the absence of instruction tuning.

Final decision Declare the base-pretraining phase complete. Freeze best.safetensors as WAI-125M Base v1.0. Begin the evaluation phase before changing the weights, then create a separately versioned WAI-125M Instruct model.

Immediate next actions

  • Calculate exact test.bin loss and perplexity.
  • Create the Hugging Face-compatible WAI-125M package and model card.
  • Run a 100-example benchmark smoke test, then full benchmark suites.
  • Build and audit the SFT dataset before starting instruction tuning.
  • Add KV-cache generation, quantize, and measure GTX 1650 latency and VRAM.
